Issue #$ARGUMENTS の実装後検証を行ってください。

**`/4` で実装・品質チェック完了後、`/6`（PR作成）前に必ず実行するコマンドです。**

---

## 概要

実装の品質を PR 作成前に検証し、CI だけでは検出できない設計上の問題を事前に潰します。

---

## 手順

### Step 1: 変更内容の把握

```bash
gh issue view $ARGUMENTS --comments
git diff main --stat
```

変更の規模とレイヤーを確認する。

### Step 2: 構成・配置チェック

新規ファイル・変更ファイルが正しいディレクトリ構成とルールに従っているか確認する。
ルール参照: `.claude/rules/file-naming.md`

**チェック項目:**

| チェック | 確認内容 |
|---------|---------|
| ディレクトリ構成 | Backend: `api/`, `services/`, `schemas/`, `infrastructure/models/`, `infrastructure/repositories/`, `tests/` の分離 |
| ファイル配置 | 正しいレイヤーに配置されているか（例: ビジネスロジックが `api/` に漏れていないか） |
| 命名規則 | Python: スネークケース、TS: キャメル/パスカル、ドキュメント: ケバブケース |
| 重複チェック | 同じロジック・定義が複数箇所に存在しないか |
| import整理 | 不要な import、循環参照がないか |

**重複チェックの観点:**

```
- 同じバリデーションロジックが API 層とサービス層の両方にないか
- 同じ定数・マジックナンバーが複数ファイルに散在していないか
- 同じクエリパターンが複数のリポジトリメソッドにないか
- 同じ型定義（Pydantic schema）が別名で重複していないか
- converter/mapper が不要に重複していないか
```

**具体的な確認方法:**

```bash
# 新規・変更ファイル一覧
git diff main --name-only

# Backend: ディレクトリ構成の確認
git diff main --name-only | grep "apps/backend"

# Frontend: Private Folder 構成の確認
git diff main --name-only | grep "apps/frontend"
```

問題があれば修正してから次のステップへ。

### Step 3: 実装後検証（エージェントチーム）

**複数レイヤーにまたがる変更**の場合はエージェントチームで検証を実施。
詳細: `.claude/rules/agent-teams.md`

**バックエンド（Model + Service + API + Migration + Test）:**
```
Issue #$ARGUMENTS の実装をチームで検証して。
- スキーマ担当: Model定義、マイグレーション、既存モデルとの整合性
- サービス担当: ロジック、DI、トランザクション、エラーハンドリング
- API担当: エンドポイント設計、テストカバレッジ、認証認可
- 横断チェッカー: 各担当の報告を突き合わせ、レイヤー間の隙間を指摘
- テスト実行担当: make test を実行し、pass/fail を確認
```

**フロントエンド（page + Container/Presentational + hooks + API連携）:**
```
Issue #$ARGUMENTS のフロントエンド実装をチームで検証して。
- コンポーネント担当: Container/Presentational 分離、Private Folder 構成の準拠
- データフェッチ担当: Server/Client 境界、キャッシュ戦略、ローディング/エラー状態
- UI/UX担当: レスポンシブ、アクセシビリティ、デザインシステム準拠
- 横断チェッカー: API契約との整合性、型の一貫性、状態管理の漏れ
```

**オプション検証（必要に応じて追加）:**

| 検証タイプ | 追加担当 | 適用条件 |
|-----------|---------|---------|
| テストカバレッジ | `test-coverage-checker` | Backend変更で新しいコードが追加された場合。`make test-coverage` 実行後、カバレッジレポートを分析し、未テスト箇所を指摘 |
| セキュリティ | `security-reviewer` | Backend API 変更時。認証・認可漏れ、インジェクション、データ露出リスクを検証 |
| 互換性 | `compatibility-checker` | 既存 API/スキーマの変更時。破壊的変更がないか、クライアントへの影響を検証 |

**検証結果への対応:**
- 必須修正 → 修正してから次のステップへ
- 推奨 → 判断して対応
- 参考 → 記録のみ
- スコープ外 → 下記の判断基準で対応

**スコープ外の改善が見つかった場合:**

| 条件 | アクション |
|------|-----------|
| **本Issueの実装に直接関連する問題**（ドキュメント欠落、型定義の不整合など） | **スコープ外にせず本Issue内で対応** |
| 軽微で無関係（1-2ファイル、数行の修正、typo・命名修正） | その場で修正OK |
| 大きくて無関係（新機能、設計変更、PRの差分が大幅に増える） | 新Issue作成（`/1`）して現Issueにリンク。**ラベル・Projects設定を忘れずに** |

> 注意: 「スコープ外」の判断基準: 本Issueで実装した機能に関連するかどうか。関連する問題は規模に関わらず本Issue内で対応すべき。

> 新Issue作成時のチェック: ラベル、GitHub Projects の Status/Stage/Feature/Priority を設定すること。

> 単一レイヤーの軽微な変更（1-3ファイル）であればエージェントチーム検証はスキップ可。ただし Step 2 の構成チェックは必ず実施する。

### Step 4: DocDD 整合性確認

> **前提**: `/4` の実装時に、実装に対応する DocDD（DM/API仕様/UC/SR）は更新済みであること。
> このステップは「更新漏れがないかの確認」であり、ここで初めてドキュメントを書く場ではない。

DocDD 文書との整合性を **2段階** でチェック。

#### Step 4-1: 構造チェック（自動）

`make traceability` で構造的なリンク切れを自動チェック：

```bash
make traceability
```

- エラーがある場合は差し戻し
- 警告がある場合は内容を確認して判断

#### Step 4-2: 内容チェック（エージェントチーム）

**DocDD 関連ドキュメントがある場合のみ実施**（なければスキップ）

ドキュメントと実装の**意味的整合性**を検証：

```
Issue #$ARGUMENTS のドキュメントと実装の整合性をチームで検証して。
- doc-reader: docs/7-axis/ の BR/UC/DM/SR を読み、仕様を整理
- code-reader: 実装を読み、実際の挙動を整理
- diff-checker: 両者の報告を突き合わせて乖離を分類

検証項目:
- DM定義（エンティティ・属性・制約）vs 実装の型・スキーマ
- API仕様（パラメータ・レスポンス）vs 実装のエンドポイント
- ビジネスルール vs サービス層のロジック
- UC の事前条件・事後条件 vs テストケース

乖離の分類:
- Doc先行（仕様あり→実装なし）: 実装を追加 or 仕様を次Issueに回す
- Code先行（実装あり→仕様なし）: ドキュメントを更新
- 不一致（両方あるが内容が違う）: どちらが正しいか判断して修正

重要: 乖離の対応判断
- 本Issueで実装した機能に直接関連するドキュメントの乖離 → 本Issue内で対応（スコープ外にしない）
- 本Issueとは無関係な既存ドキュメントの乖離 → 別Issue化してOK
```

> `make traceability` は構造的なリンク切れ（`traces_to`/`traces_from` の整合性）のみ検出。**内容の一致**（仕様と実装が意味的に合っているか）はエージェントチームでしか判断できない。

#### Step 4-3: 検証結果の記録

**エージェントチーム検証を実施した場合のみ実施**

検証結果を Issue コメントとして記録し、後から振り返れるようにする：

```bash
gh issue comment $ARGUMENTS --body "$(cat <<'EOF'
## 実装後検証結果（/5）

### Step 2: 構成・配置チェック
- ✅ ディレクトリ構成準拠
- ✅ 命名規則準拠
- [必要に応じて重複チェック結果を記載]

### Step 3: エージェントチーム検証
- [役割名]: [簡潔な評価]

**総評**: X件 / Y件 / Z件

### Step 4: DocDD 整合性
- Step 4-1（構造チェック）: `make traceability` [結果]
- Step 4-2（内容チェック）: [実施/スキップ] [結果概要]

---
*検証実施日時: $(date +%Y-%m-%d)*
EOF
)"
```

### Step 5: Pencil 整合性検証

**Pencil 画面がある Issue の場合のみ実施**（なければスキップ）

Pencil と実装が一致しているかを**検証**する（修正は `/4` で実施済みの前提）。
参照: `.claude/rules/project-workflow.md` の「Pencil 調整ルール」

**検証手順:**

1. Issue に記載された Pencil 画面 ID を `batch_get` で読み取る
2. `get_screenshot` で Pencil の現状を確認
3. 実装結果と Pencil デザインを比較し、一致を確認

**乖離が残っている場合**（`/4` で漏れた修正）:

| 乖離パターン | 対応 |
|:---:|------|
| **Pencil に不足**（実装で追加した UI 要素が Pencil にない） | Pencil に追加 |
| **Pencil が過剰**（実装で不要と判断した UI 要素が Pencil に残っている） | Pencil から削除 |
| **仕様変更**（実装中に仕様が変わった） | Pencil を実装に合わせて更新 |

4. `batch_design` で Pencil を更新 → `get_screenshot` で確認ゲート

> **役割分担**: `/4` で Pencil 更新、`/5` Step 5 で一致を検証。
> ここで修正が必要になるのは `/4` での更新漏れのケース。

### Step 6: 差分確認・Issue 更新

計画との差分がある場合は `/update-issue $ARGUMENTS` でIssue本文を更新：
- 当初計画と異なる実装になった場合
- 追加の決定事項が出た場合
- 予期しない問題が発生した場合
- 検証で修正した内容
- Pencil 更新があった場合

### Step 7: Codex コードレビュー

実装検証の最終ステップとして、Codex CLI でコード差分をレビューする。
ルール参照: `.claude/rules/codex-review.md`

**Codex 利用可否を判定:**

```bash
codex --version > /dev/null 2>&1
```

#### Codex が利用可能な場合

1. Codex review を実行:

```bash
codex review --base main
```

> **注意**: Codex の応答には 3〜5 分かかる場合がある。30 秒で応答なしと判定しないこと。
> **注意**: `--base` と `[PROMPT]` の同時使用は不可。プロンプト指定なしで実行する。

2. 結果を Issue コメントに構造化記録:

```bash
gh issue comment $ARGUMENTS --body "$(cat <<'EOF'
## Codex コードレビュー結果

### 指摘一覧
- [🔴/🟡/🟢 指摘内容]

### 対応
- 🔴 → [修正内容]
- 🟡 → [対応/非対応の判断理由]

---
*Codex CLI review (`codex review --base main`): $(date +%Y-%m-%d)*
EOF
)"
```

3. 🔴 必須の指摘がある場合:
   - 修正を実施
   - テストを再実行して合格を確認
   - 修正内容を Issue コメントに追記

#### Codex が利用不可の場合（Fallback）

**サイレントスキップ禁止** — 必ずユーザーに通知する。

1. `.claude/templates/codex-review-handoff.md` の「コードレビュー」セクションを出力
2. ユーザーに手動で Codex / ChatGPT にレビューを依頼するよう案内

```
⚠️ Codex CLI が未導入のため、コードレビューを自動実行できません。
以下の handoff テンプレートを使って手動レビューを実施してください。
```

観点メモ: `.claude/templates/codex-verify-review-prompt.md`

## チェックリスト

`/6` に進む前に確認：
- [ ] ディレクトリ構成・ファイル配置がルールに沿っている
- [ ] 重複したロジック・定義がない
- [ ] 実装後検証を実施した（複数レイヤー変更の場合）
- [ ] 検証で指摘された必須修正を対応した
- [ ] DocDD 整合性を確認した（関連ドキュメントがある場合）
- [ ] Pencil 整合性を確認した（Pencil 画面がある場合）
- [ ] 計画との差分があれば Issue を更新した
- [ ] Codex コードレビューを実施した（または Fallback handoff を出力した）
- [ ] テストが引き続きパスしている（修正した場合は再実行）

検証通過後:
```bash
/6 $ARGUMENTS    # PR 作成
```

Remember to use the GitHub CLI (`gh`) for all GitHub-related tasks.
