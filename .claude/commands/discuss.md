## `/brainstorm` との棲み分け

| 観点 | `/discuss` | `/brainstorm` |
|------|-----------|--------------|
| **タイミング** | 開発中（実装方針に迷ったとき） | Issue 起票前（必須 discovery） |
| **目的** | 既存方針の壁打ち・選択肢比較 | アイデア発散 → スコープ絞り込み → Issue 化準備 |
| **出力** | 選択肢の比較・推奨方針・抜け漏れチェック | Goal / Non-goals / Options / Chosen direction / Risks / Issue split |
| **次のステップ** | `/develop`（実装続行）/ `/update-issue`（既存 Issue 更新） | `/issue`（起票） |
| **ユーザー発話例** | 「〇〇方式と××方式、どっちが良い？」 | 「〇〇したいんだけど、どこから手を付ければ？」 |

> **迷ったら**: 「既に Issue がある / 実装中」なら `/discuss`。Issue がまだないなら、スコープが明確でも `/brainstorm`。

## このコマンドの目的

開発中に生じた疑問・迷い・不安を解消するための壁打ちセッションです。

**使うタイミング:**
- 実装方針に迷った時
- 複数のアプローチがあり選べない時
- 「これで合ってる？」と確認したい時
- 抜け漏れがないか確認したい時
- 別の観点からのフィードバックが欲しい時

---

## 相談の進め方

### 1. 状況を説明してもらう

相談内容を聞き、以下を確認：
- 何を実現したいか
- 現在どこまで進んでいるか
- 何に迷っているか

### 2. 選択肢を提示

複数のアプローチがある場合は、それぞれのメリット・デメリットを整理：

```
## 選択肢

### A: [アプローチ名]
- メリット: ...
- デメリット: ...
- 適したケース: ...

### B: [アプローチ名]
- メリット: ...
- デメリット: ...
- 適したケース: ...

## 推奨
[理由とともに推奨を提示]
```

### 3. 抜け漏れチェック

以下の観点から確認：
- セキュリティ面
- パフォーマンス面
- 保守性・拡張性
- テスト容易性
- 既存コードとの一貫性

### 4. リサーチ（必要時）

公式ドキュメントやベストプラクティスを調査し、根拠のある提案を行う。

**リサーチの手段:**
- **WebSearch**: 公式ドキュメント・ベストプラクティス・既知の問題を検索
- **WebFetch**: 公式ドキュメントの該当ページを取得して詳細を確認
- **コードベース調査**: Grep/Glob で既存の実装パターンを確認

### 5. エージェント活用（複雑な相談の場合）

複数の観点から検討が必要な場合、エージェントを活用：

**サブエージェント（並列リサーチ）:**
- 複数候補のライブラリ・パターンを同時に調査
- 既存コードベースの影響範囲を並列で探索

**エージェントチーム（設計壁打ち）:**
- パフォーマンス観点 vs セキュリティ観点など、異なる視点からの並列レビュー
- `.claude/rules/agent-teams.md` パターン2「設計壁打ち」を参照

## 相談のコツ

**ユーザー向け:**
- 「〇〇しようと思うけど、どう思う？」のように具体的に
- コードや設計案があれば共有する
- 迷っているポイントを明確に

**Claude向け:**
- 一方的に答えを出さず、対話的に進める
- 「他に考慮すべき点はありますか？」と確認を促す
- ユーザーの意図を確認してから提案する

## 関連コマンド

- `/plan`: 計画立案（Phase 2 で相談フェーズあり）
- `/develop`: 実装（途中で困ったら `/discuss` へ）
- `/update-issue`: 相談の結果をIssueに反映
