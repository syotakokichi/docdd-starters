# Receiving Code Review

## 概要

コードレビューは技術的評価であり、感情的パフォーマンスではない。

**原則: 実装前に検証する。仮定する前に質問する。社交的快適さより技術的正確性。**

---

## 使い方

以下の場面でこのスキルが適用される:

- `/review`（独立レビュー）の指摘を受け取ったとき
- `/plan` Phase 5（Codex レビュー）の指摘を受け取ったとき
- PR の GitHub レビューコメントを受け取ったとき
- ユーザーからの直接的なコード修正指示を受けたとき

---

## 6ステップ受領パターン

```
レビュー指摘を受け取ったとき:

1. READ:       指摘全体を反応せずに読む
2. UNDERSTAND: 要件を自分の言葉で言い換える（不明なら質問）
3. VERIFY:     コードベースの実態と照合する
4. EVALUATE:   このコードベースにとって技術的に正しいか？
5. RESPOND:    技術的な確認 or 理由付きの反論
6. IMPLEMENT:  1項目ずつ実装し、各修正をテスト
```

---

## 禁止される応答

**使ってはいけない表現:**
- 「おっしゃる通りです！」（パフォーマティブな同意）
- 「素晴らしい指摘です！」（感情的リアクション）
- 「すぐに実装します」（検証前の実装宣言）
- 検証前の空疎な同意・謝意（「ありがとうございます」「おっしゃる通りです」等）

**代わりに:**
- 技術的な要件を言い換える
- 明確化のための質問をする
- 技術的根拠に基づいて反論する
- 言葉より行動で示す（修正して見せる）

## ソース別ハンドリング

### ユーザーからの指摘

- **信頼**: 理解した上で実装する
- **スコープが不明確なら質問**する
- **パフォーマティブな同意はしない**
- **アクションに直行**する or 技術的な確認のみ

### `/review`（独立レビュー）からの指摘

```
指摘を受け取ったら:
  1. P1/P2/P3 + 残留リスクの分類を確認
  2. 指摘対象のコードを実際に読む
  3. 指摘が正しいか、コードベースで検証
  4. 正しければ **本セッション内で即修正**、誤りなら技術的根拠で反論
  5. 修正後に verify script / quality gate を再実行して GREEN 継続を確認
  6. 修正内容を Issue コメントで報告
```

**デフォルトは即適用**。P1 / P2 で actionable な修正案（reviewer が具体的な変更方針を提示 / 本 Issue スコープ内 / 既存 design intent と衝突しない）は**ユーザー承認を待たずに修正する**。

「ユーザー判断待ち」に逃げていい例外は [→ `/review` / `/verify` 共通: ユーザー判断を仰ぐ 4 例外（SSOT）](#review-verify-4-exceptions-ssot) を参照。

これらに該当しない限り、**報告だけして停止するのは逸脱**。`/review` Step 4「P1 / P2 は must fix」を Step 5 反映で実行動に落とすのが受領側の責務。

### `/verify`（Codex 単独レビュー）からの指摘

本テンプレートの `/verify` Step 5 は **Codex CLI 単独** によるコード差分レビューで、分類体系は `🔴 必須 / 🟡 推奨 / 🟢 参考 / ❌ 誤検知` の 4 段階（[`.claude/rules/codex-review.md`](../../rules/codex-review.md) SSOT）。

```
指摘を受け取ったら:
  1. 🔴/🟡/🟢/❌ の分類を確認
  2. 指摘対象のコードを実際に読む
  3. 指摘が正しいか、コードベースで検証
  4. 🔴 必須 の actionable fix は **本セッション内で即修正**（`/review` に委譲しない）
  5. 🟡 推奨 は対応するか「理由付きで見送り」かを判断し、Issue コメントに記録
  6. 修正後に該当する quality gate（`make test-backend` / `make test-frontend` / `make validate-claude` / `make traceability` のいずれか）を再実行して GREEN 継続確認
  7. 🟢 参考 は記録のみ（対応任意）
  8. ❌ 誤検知は理由を記録して無視
```

**デフォルトは即適用**。`/verify` は `/review` に渡る前の最後の実装検証関門であり、🔴 必須は本セッション内で修正完了させるのが責務。

「`/review` に委譲」「ユーザー判断待ち」に逃げていい例外は [→ `/review` / `/verify` 共通: ユーザー判断を仰ぐ 4 例外](#review-verify-4-exceptions-ssot) を参照。

これらに該当しない限り、**🔴 必須を `/review` に回して本セッションで修正しないのは逸脱**。`/verify` Step 5（[`.claude/commands/verify.md`](../../commands/verify.md)）+ `codex-review.md` の must fix 方針を実行動に落とすのが受領側の責務。

> **3 reviewer 並列レビュー** (Codex + Claude SA × 2 の adversarial review) は本テンプレートでは未導入で、後続フェーズ（D-1 想定）で導入予定。本節は単一 Codex reviewer 文脈で記述している。3 reviewer 想定の追加分類（🔵 既存踏襲 等）と機械検証 SSOT は本ファイル末尾の forward reference 表に集約する。

<a id="review-verify-4-exceptions-ssot"></a>

### `/review` / `/verify` 共通: ユーザー判断を仰ぐ 4 例外

`/verify` Step 5 / `/review` Step 4 で受け取った指摘について、**以下のいずれかに該当する場合のみ**、本セッションで即適用せず次フェーズ（`/review` に委譲 / ユーザー判断待ち）に委ねる。

| # | キー | 例外名 |
|---|---|---|
| 1 | `issue_scope_expansion` | スコープ超過（別 Issue 候補） |
| 2 | `prior_user_design_conflict` | 過去のユーザー design 判断との明示的な衝突 |
| 3 | `reviewer_disagreement` | 複数 reviewer 間で対応策が対立し統合判断が割れる（3 reviewer 並列レビュー導入後に有効化） |
| 4 | `issue_sizing_overflow` | 別 Issue 化相当の修正サイズ（[`issue-sizing`](../issue-sizing/SKILL.md) 上限超過） |

これらに該当しない限り、各節の「逃げ禁止」責務宣言が発動し、**本セッション内で即適用するのが受領側の責務**。

**例外に該当した場合のみ**、文脈共通で **ユーザー判断待ちに切り替える**（受領は本セッションで完結させない）:

| 文脈 | 例外非該当時 | 例外該当時 |
|------|------------|----------|
| `/verify` Step 5 | 🔴 必須は本セッションで即適用・修正完了（`/review` への自動委譲は禁止） | ユーザー判断待ち（`/review` への bypass は逃げ道として使わない） |
| `/review` Step 4 | P1 / P2 は本セッションで即適用・修正完了（「ユーザー判断待ち」を理由なく宣言しない） | ユーザー判断待ちとして明示的に保留する |

つまり `/verify` から `/review` への defer は 4 例外でも非該当でも認めない。`/review` は独立レビューであり、未解消指摘の bypass 先ではない。

> 🟠 各キーの `description` / `allowed_when` / `must_not_use_when` / `non_examples` の機械検証可能な SSOT（YAML + validator）と、Issue コメント / PR body 間の grammar 差分（surface 別 marker grammar）は本テンプレートでは未導入。後続フェーズ（D-1 想定）で導入する 4 ファイルは本ファイル末尾の forward reference 表に集約する。

### `/plan` Phase 5（Codex レビュー）からの指摘

```
指摘を受け取ったら:
  1. 🔴/🟡/🟢/❌ の分類を確認
  2. 🔴 必須 → 計画に反映（対応必須）
  3. 🟡 推奨 → 対応するか理由付きで見送り
  4. 🟢 参考 → 記録のみ（対応任意）
  5. ❌ 誤検知 → 理由を記録して無視
```

### PR の GitHub レビューからの指摘

```
実装前に:
  1. このコードベースにとって技術的に正しいか？
  2. 既存の機能を壊さないか？
  3. 現在の実装に理由があるか？
  4. 全プラットフォーム/バージョンで動くか？
  5. レビュアーが全コンテキストを理解しているか？

指摘が誤りだと判断したら:
  技術的根拠で反論する

検証できない場合:
  「X なしでは検証できません。[調査/質問/続行] すべきでしょうか？」

ユーザーの過去の設計判断と矛盾する場合:
  ユーザーに相談してから対応する
```

## 分類マッピング

本テンプレートでは、指摘のソースに応じて異なる分類体系を使用する。

| コマンド文脈 | 分類体系 | 用途 |
|------------|---------|------|
| `/review`（独立レビュー） | P1 / P2 / P3 + residual risk | 重大度ベース |
| `/plan` Phase 5（Codex レビュー） | 🔴 必須 / 🟡 推奨 / 🟢 参考 / ❌ 誤検知 | 対応要否ベース |
| `/verify` Step 5（Codex 単独レビュー） | 🔴 必須 / 🟡 推奨 / 🟢 参考 / ❌ 誤検知 | 対応要否ベース（`/plan` Phase 5 と同体系） |

> `/verify` 自身の品質チェック（`make test-backend` / `make validate-claude` 等）の結果ステータス（`PASS / N/A / 未解消`）はレビュー指摘分類ではなく **検証エビデンスの結果値**。`verification-result-comment.md` 表のセル値であり、本表の対象外。

### 分類の対応関係

| `/review` | `/plan` Phase 5 | 意味 | 対応レベル |
|-----------|-----------------|------|-----------|
| P1（重大） | 🔴 必須 | 対応しないとリリースできない | must fix |
| P2（中程度） | 🟡 推奨 | 対応が望ましい | `/review`: must fix / `/verify` Step 5: actionable なら即適用（4 例外時のみユーザー判断待ち）/ `/plan` Phase 5: 理由付きで見送り可 |
| P3（軽微） | 🟢 参考 | 品質向上に寄与するが必須ではない | should fix or residual risk |
| — | ❌ 誤検知 | 指摘自体が不正確 | 却下 |

> **注意**: `/review` の P1/P2 は **must fix**（未解消なら `/pr` に進めない）。`/plan` Phase 5 の 🟡 は「理由付きで見送り可」。同じ行にマッピングされているが、**対応レベルはソースによって異なる**。

### 応答時の分類選択

指摘を受け取ったら、**ソースに応じた分類体系で応答する**:

- `/review` の指摘には → P1/P2/P3 で応答
- `/plan` Phase 5 の指摘には → 🔴/🟡/🟢/❌ で応答
- `/verify` Step 5（Codex 単独レビュー）の指摘には → 🔴/🟡/🟢/❌ で応答（`/plan` Phase 5 と同体系）

> `/verify` の品質チェック行（`make test-backend` 等）の結果値は `PASS / N/A / 未解消` を使うが、これはレビュー指摘の分類ではなく検証エビデンスの結果値。混同しない。

## 不明確な指摘への対応

```
指摘の一部が不明確な場合:
  まだ何も実装しない
  不明確な項目について質問する

理由: 項目間に関連がある可能性がある。
      部分的な理解 = 誤った実装
```

**例:**
```
ユーザー: 「1-6 を修正して」
1,2,3,6 は理解できる。4,5 が不明確。

❌ 間違い: 1,2,3,6 を実装し、4,5 は後で質問
✅ 正しい: 「1,2,3,6 は理解しました。4 と 5 について確認させてください」
```

## YAGNI チェック

```
レビュアーが「適切に実装すべき」と提案した場合:
  コードベースで実際の使用箇所を検索する

  未使用 → 「このエンドポイントは呼ばれていません。削除すべきでは？（YAGNI）」
  使用中 → 適切に実装する
```

---

## 実装順序

```
複数項目の指摘がある場合:
  1. 不明確な項目をまず質問する
  2. 以下の順序で実装:
     - ブロッキング問題（機能停止、セキュリティ）
     - 単純な修正（タイポ、import）
     - 複雑な修正（リファクタリング、ロジック）
  3. 各修正を個別にテスト
  4. リグレッションがないことを確認
```

## 反論すべき場面

以下の場合は反論する:

- 指摘が既存機能を壊す
- レビュアーが全コンテキストを持っていない
- YAGNI に違反する（未使用機能）
- このスタックにとって技術的に不正確
- レガシー/互換性の理由がある
- ユーザーのアーキテクチャ判断と矛盾する

**反論の仕方:**
- 防御的にならず、技術的根拠を使う
- 具体的な質問をする
- 動作するテスト/コードを参照する
- アーキテクチャ的な問題はユーザーを巻き込む

---

## 正しい指摘を認めるとき

```
✅ 「修正しました。[変更内容の簡潔な説明]」
✅ 「確認しました — [具体的な問題]。[場所] で修正済み」
✅ [修正してコードで示す]

❌ 「おっしゃる通りです！」
❌ 「素晴らしい指摘です！」
❌ 「ご指摘ありがとうございます！」
```

---

## 反論が間違っていた場合

```
✅ 「確認したところ正しいです。[X] を調べて [Y] を確認しました。修正します」

❌ 長い謝罪
❌ なぜ反論したかの弁明
❌ 過度な説明
```

事実を述べて先に進む。
