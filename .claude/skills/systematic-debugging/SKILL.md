# Systematic Debugging

## 概要

場当たり的な修正は時間を浪費し、新たなバグを生む。

**原則: 修正の前に根本原因を特定する。症状の修正は失敗。**

---

## 使い方

以下のすべての技術的問題に適用する:

- テスト失敗
- 本番バグ
- 予期しない挙動
- パフォーマンス問題
- ビルド失敗
- 外部連携エラー（外部 API / Webhook / コールバック / クラウドサービス）

**特に使うべき場面:**
- 時間的プレッシャーがあるとき（急ぐほど推測に走りやすい）
- 「すぐ直せそう」に見えるとき
- すでに複数回修正を試みたとき
- 前回の修正が効かなかったとき

---

## 4フェーズプロセス

各フェーズを完了してから次に進む。

### Phase 1: 根本原因の調査

**修正を試みる前に必ず実施する。**

1. **エラーメッセージを注意深く読む**
   - スタックトレースを最後まで読む
   - 行番号、ファイルパス、エラーコードを記録する
   - エラーメッセージ自体に解決策が含まれていることが多い

2. **一貫した再現手順を確立する**
   - 毎回同じ手順で再現できるか？
   - 再現不能 → データを追加収集する。推測しない

3. **直近の変更を確認する**
   - `git diff`、最近のコミット
   - 新しい依存関係、設定変更
   - 環境の差異

4. **多コンポーネントシステムでの証拠収集**

   本テンプレートは複数コンポーネントにまたがる:

   | レイヤー | 確認対象 |
   |---------|---------|
   | Frontend (Next.js) | Console エラー、Network リクエスト |
   | Backend (FastAPI) | リクエストログ、例外トレース |
   | DB (PostgreSQL) | クエリエラー、制約違反 |
   | 外部連携 | 外部 API レスポンス、Webhook、コールバック |

   **各コンポーネント境界で入出力を確認してから、故障箇所を特定する。**

5. **データフローを追跡する**
   - 不正な値がどこで発生したか？
   - 何がその値を渡したか？
   - 源泉まで遡って、源泉で修正する（症状の場所ではなく）

### Phase 2: パターン分析

1. **動作する類似コードを探す**
   - 同じコードベース内で同様のパターンが動いている箇所を特定
   - 何が動いていて、壊れているものと何が違うか？

2. **リファレンス実装と比較する**
   - パターンを実装している場合、リファレンスを完全に読む（飛ばし読みしない）

3. **差分を特定する**
   - 動作するものと壊れているものの差分をすべて列挙
   - 「これは関係ない」と仮定しない

4. **依存関係を理解する**
   - このコンポーネントが必要とする他のコンポーネントは？
   - 設定、環境変数、前提条件は？

### Phase 3: 仮説とテスト

1. **単一の仮説を立てる**
   - 「X が根本原因だと考える。理由は Y」と明確に記述する

2. **最小限の変更でテストする**
   - 仮説を検証する最小の変更を行う
   - 一度に1つの変数だけ変える
   - 複数の修正を同時にしない

3. **続行前に検証する**
   - 効いた → Phase 4 へ
   - 効かなかった → **新しい仮説**を立てる。追加修正を重ねない

4. **わからないとき**
   - 「X がわからない」と正直に言う
   - 知ったふりをしない
   - 追加調査する

### Phase 4: 修正の実装

1. **失敗するテストケースを作成する**
   - 最も単純な再現ケース
   - `tdd-workflow` スキルの RED-GREEN パターンに従う
   - テストなしの修正は定着しない

2. **単一の修正を実装する**
   - 特定された根本原因に対処する
   - 一度に1つの変更
   - 「ついでに」の改善をしない

3. **修正を検証する**
   - `verification-before-completion` スキルの5ステップゲートに従う
   - テストがパスするか？
   - 他のテストが壊れていないか？

4. **修正が効かない場合 → カウントする**
   - 3回未満: Phase 1 に戻り、新情報で再分析
   - **3回以上: 中断してアーキテクチャを疑う（Step 5 へ）**
   - 4回目の修正を試みない

5. **3回以上失敗: アーキテクチャを疑う**

   **アーキテクチャ問題のサイン:**
   - 各修正が異なる場所で新しい共有状態/結合/問題を露呈する
   - 修正に「大規模リファクタリング」が必要になる
   - 各修正が別の場所で新たな症状を生む

   **ユーザーに相談する:**
   - このパターンは根本的に健全か？
   - 惰性で続けていないか？
   - 症状修正を続けるより、アーキテクチャをリファクタすべきか？

   **エージェントチーム昇格**（`agent-teams` skill パターン 4: 競合仮説でのデバッグ）:
   - 複雑なバグで、異なる仮説を並列調査してほしい場合
   - 競合仮説デバッグパターンを使用

## 危険信号 - 止まってプロセスに戻る

以下のことを考えている自分に気づいたら、Phase 1 に戻る:

- 「とりあえず X を変えてみよう」
- 「今は応急処置で、後で調査しよう」
- 「複数の変更を入れて、テストを回そう」
- 「テストは省略して、手動で確認しよう」
- 「たぶん X が原因だから、直してみよう」
- 「完全には理解していないけど、これで動くかも」
- 「もう1回だけ修正を試そう」（すでに2回以上試した後）

---

## よくある合理化

| 言い訳 | 現実 |
|--------|------|
| 「単純な問題だからプロセス不要」 | 単純なバグにも根本原因がある |
| 「緊急だからプロセスの時間がない」 | 体系的デバッグのほうが推測より速い |
| 「まずこれを試してから調査する」 | 最初の修正がパターンを決める。最初から正しくやる |
| 「修正を確認してからテストを書く」 | テストなしの修正は定着しない |
| 「複数修正を同時にやれば時間短縮」 | 何が効いたか分離できない。新バグの原因になる |
