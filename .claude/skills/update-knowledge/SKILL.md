# ナレッジ更新スキル

## 概要

セッション中に得た知見（新しいパターン、ハーネス改善、フィードバック等）を、既存のスキル・ルール・コマンド・テンプレートに反映する。

今回限りの情報ではなく、**次回以降のセッションでも再利用できる知見**を対象とする。

### 非ゴール

- コードのリファクタリング（実装変更は `/develop` で行う）
- 一時的な調査メモの保存（memory で行う）
- 新規スキル・ルールの設計（別途 Issue で行う）

### コマンド実行中の即時修正との棲み分け

| トリガー | スコープ | 例 |
|---------|---------|-----|
| **コマンド実行中に手順の不備に気づいた**（即時修正） | 該当コマンド / スキルの手順修正 | `/develop` の前提条件が不足している |
| **update-knowledge**（体系的反映） | ハーネス全体（skills / rules / commands / templates） | 新しい実装パターンを発見した |

コマンド実行中の即時修正は「不備の即時修正」、update-knowledge は「知見の体系的反映」。前者の SSOT 化は本テンプレートでは未導入で、後続フェーズで rule 化予定。

## 使い方

| シーン | トリガーワード |
|--------|--------------|
| 実装中に有用なパターンを発見した | 「ハーネス更新して」「学びを反映して」 |
| ユーザーからフィードバックを受けた | 「スキル更新して」「ナレッジ更新」 |
| 新しいツール / ライブラリの使い方を学んだ | 「この知見を残して」 |
| コマンドの手順改善（コマンド実行中の即時修正経由） | 自動トリガー |

## 詳細

### 更新対象の判断

| 種類 | 例 | 更新先 |
|------|-----|--------|
| バックエンドの実装パターン | FastAPI の DI パターン、SQLAlchemy の使い方 | `skills/backend-patterns/` |
| フロントエンドの実装パターン | App Router の新しい使い方、Container/Presentational | `skills/frontend-patterns/` |
| テスト戦略・パターン | フィクスチャ改善、marker 運用 | `skills/testing-patterns/` or `skills/tdd-workflow/` |
| デザイン / UI 設計 | Pencil.dev MCP 連携、デザイントークン管理 | `skills/design/` |
| DocDD 運用知見 | 軸間のリンク方法、frontmatter の書き方 | `skills/docdd-workflow/` |
| コマンド手順の改善 | ステップ追加、前提条件明記 | `commands/*.md` |
| チーム規約・命名の改善 | 命名パターン、品質基準 | `rules/*.md` |
| テンプレート改善 | Issue / PR / コメントの型 | `templates/*.md` |
| ユーザーの好み（セッション横断） | 出力スタイル、確認の頻度 | memory |
| プロジェクト状況・外部参照 | 進行中の作業、外部 URL | memory |

### 更新しないもの

| 種類 | 理由 | 代わりに |
|------|------|---------|
| 今回だけの一時的な情報 | 再利用されない | 不要（会話内で完結） |
| コードから読み取れること | ファイルを見れば分かる | 更新不要 |
| git 履歴で追えること | `git log` で確認できる | 更新不要 |
| CLAUDE.md に既に書かれていること | 重複になる | 更新不要 |
| エフェメラルなタスク状態 | 会話内で完結する | TodoWrite で管理 |

### 更新フロー

```
1. セッション中の学びを整理
   - 何が新しい知見か
   - 次回以降に再利用できるか
   ↓
2. 更新先を特定
   - 上記マッピング表で該当ファイルを特定
   - 複数ファイルにまたがるか確認
   ↓
3. 既存ファイルを読んで現状を把握
   - 重複する内容がないか
   - どこに追加するのが自然か
   ↓
4. 更新を実施
   - 既存の構成・フォーマットに合わせて追記
   - 関連ファイル間の整合性を保つ
   ↓
5. 変更サマリーをユーザーに報告
   - 何をどこに反映したか一覧で提示
```

### memory との棲み分け

| 保存先 | 対象 | 例 |
|--------|------|-----|
| **skills / rules / commands** | 再利用可能な実行知識・手順・パターン | 「integration テストは `@pytest.mark.integration` marker を付与し、CI では `make test-backend` で実行する」 |
| **memory** | ユーザーの好み・プロジェクト状況・外部参照 | 「ブラウザ確認は N/A にする前に確認を取る」 |

**判断基準**: 「他の開発者が同じプロジェクトで作業しても役立つか？」
- Yes → skills / rules / commands（プロジェクト知識）
- No（このユーザー固有）→ memory

### 更新時の原則

| 原則 | 説明 |
|------|------|
| 既存の構成に合わせる | 新しいセクションを乱立しない。既存の表やリストに追記 |
| 関連ファイル間の整合性 | `skills/README.md` のスキル一覧テーブルを正本とし、`references/applicable-skills.md` と同期 |
| 重複を避ける | 同じ情報を複数箇所に書かない。参照で繋ぐ |
| 最小限の変更 | 学んだことだけを追記。周辺のリファクタリングはしない |
| フォーマット準拠 | rules/ は `rules/README.md`、skills/ は `skills/README.md` の構成に従う |
