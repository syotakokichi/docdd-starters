# エージェントチーム運用スキル

## 概要

エージェントチーム機能の使い分け判断基準を定義する。
トークンコストは高いが、**議論・検証・並列作業**で単一セッションを超える品質と効率が得られる場面では積極的に活用する。

**使用箇所**: `/plan`（計画リサーチ時）、`/develop`（2レイヤー以上の並列実装時）、`/verify`（実装検証時）、`/review`（独立レビュー、別セッション必須）。

**非ゴール**: 単一ファイル修正、順序依存タスク、同一ファイル編集 — これらはチームではなく単一セッションで実施する。

## 使い方

以下のコマンドで参照される:
- `/plan` — Phase 3 のリサーチで2ソース以上に分散する場合
- `/develop` — 2レイヤー以上にまたがる実装時
- `/verify` — 2レイヤー以上の変更の検証時（コンテキストフレッシュ必須）
- `/review` — 独立レビュー（常に別セッション必須）
- `/discuss` — 設計の壁打ち（推進派・慎重派・調整役の三役分担）

## 詳細

### 3実行粒度（Execution Granularity）

| 粒度 | 適用場面 | トークンコスト |
|------|---------|:------------:|
| **タスクレベル（単一セッション）** | 1つのレイヤーで完結するタスク | 低 |
| **サブエージェントレベル** | 調査・検索など結果だけ必要なタスク | 中 |
| **チームレベル（エージェントチーム）** | 議論・検証・並列作業でメンバー間の相互作用が価値を生む場面 | 高 |

### タスクレベル（単一セッション）を使う場合

- バグ修正（1-3ファイル）
- 単一モジュール内の機能追加
- ドキュメント更新
- リファクタリング（影響範囲が限定的）

### サブエージェントレベル（Task ツール）を使う場合

- コードベースの調査・検索
- 独立した小タスクの並列実行（結果を親に返すだけ）
- テスト実行やビルドの並列化
- 各結果を**親エージェントが統合判断**すれば十分な場合

### チームレベル（エージェントチーム）を使う場合

以下の条件で判断する：

**条件A（単体で発動OK）:**
- **メンバー間の議論が有効**: 設計判断、整合性検証、仮説の突き合わせなど、結果を持ち寄って議論することで品質が上がる場面

**条件B（2つ以上で発動）:**
1. **複数レイヤーにまたがる**: Backend + Frontend + テスト等
2. **独立して並列作業できる**: ファイル競合が少ない
3. **タスクが十分に大きい**: 調整オーバーヘッドを上回る効果

> **サブエージェントとの判断基準**: 各メンバーの結果を「返すだけ」ならサブエージェント、「突き合わせて矛盾を指摘し合う」必要があるならチーム。

### エージェントチームの推奨パターン

#### 実装系

**パターン1: クロスレイヤー機能実装**

```
チームで新しいAPIエンドポイントを実装して。
- Backend担当: API + サービス層（apps/backend/app/modules/<domain>/）
- Frontend担当: 管理画面UI（apps/frontend/app/admin/）
- テスト担当: 統合テスト作成
```

**パターン2: 調査→実装パイプライン**

```
<feature> 機能をチームで開発して。
まず全員で調査フェーズを行い、発見を共有してから実装に移って。
- Phase 1（調査）: 各メンバーが既存コード・外部仕様・テストパターンを並列調査
- Phase 2（実装）: 調査結果を踏まえて担当を分けて並列実装
```

#### 検証・レビュー系

**パターン3: マイグレーション安全検証**

```
Alembic マイグレーション <revision> をチームで検証して。
- スキーマ担当: DDL とモデル定義の一致を確認
- データ担当: 既存データへの影響（NOT NULL追加、外部キー等）を検証
- ロールバック担当: downgrade が正しく動くか、本番適用手順に問題ないか確認
```

#### 分析・議論系

**パターン4: 競合仮説でのデバッグ**

```
本番で XX のエラーが発生している。
チームで異なる仮説を並列調査して、互いの仮説に反証してほしい。
```

**パターン5: 設計の壁打ち・トレードオフ分析**

```
新しいドメインモデルの設計方針をチームで検討して。
- 推進派: この設計のメリットと実現方法を主張
- 慎重派: リスクや代替案を指摘
- 調整役: 両者の意見をまとめて最適解を提案
```

**パターン6: DocDD トレーサビリティ検証**

**タイミング**: `/verify`（実装検証）の Step 4 で実施。

```
Issue #XXX のドキュメントと実装の整合性をチームで検証して。
- doc-reader: docs/7-axis/ の BR/UC/DM/SR を読み、仕様を整理
- code-reader: 実装を読み、実際の挙動を整理
- diff-checker: 両者の報告を突き合わせて乖離を分類
```

#### リサーチ・分析系

**パターン7: 技術選定・ライブラリ評価**

```
XXX の技術選定をチームで評価して。
- 候補A担当: [ライブラリA] の調査
- 候補B担当: [ライブラリB] の調査
- 評価統合役: 両者の報告を評価基準に沿って比較
```

**パターン8: 多角的リサーチ（知識統合）**

```
[テーマ] についてチームで多角的に調査して。
- 公式ドキュメント担当
- コミュニティ担当
- コードベース担当
- 統合役
```

### 運用Tips

#### Task System（依存関係付きタスク管理）

Agent Teams でタスクの実行順序を制御する場合、**依存関係（blocks / blockedBy）**を活用する。

| フィールド | 説明 | 例 |
|----------|------|-----|
| subject | タスクの主題 | "POST /api/users エンドポイント実装" |
| description | 詳細説明 | "Service層の create_user を呼び出すAPI" |
| status | 状態 | pending → in_progress → completed |
| blockedBy | 前提タスクのID配列 | ["0"] = Task 0 完了まで待機 |
| blocks | 後続タスクのID配列 | ["2", "3"] = 完了で Task 2,3 を解放 |

#### タスクサイジング

- 1メンバーあたり **5-6個のタスク** が推奨（実装・検証系）
- リサーチ系は **2-3個の調査テーマ** が推奨

#### デリゲートモード

リーダーがコードに直接触れず、**調整・統合に専念**するモード。

#### プラン承認フロー

メンバーに実装前のプラン作成を要求し、リーダーが承認してから作業開始する。

#### バックエンド検証テンプレート

```
Issue #XXX の実装をチームで検証して。
- スキーマ担当: Model定義、マイグレーション、既存モデルとの整合性
- サービス担当: ロジック、DI、トランザクション、エラーハンドリング
- API担当: エンドポイント設計、テストカバレッジ、認証認可
- 横断チェッカー: 各担当の報告を突き合わせ、レイヤー間の隙間を指摘
- テスト実行担当: make test-backend を実行し、pass/fail を確認
```

> **なぜ横断チェッカーが必要か**: レイヤー別担当だけでは「DB の UniqueConstraint 違反が API 層で 500（本来は 409）を返す」のような層をまたぐ不整合が検出できない。横断チェッカーは各担当の報告を突き合わせる専任。

#### フロントエンド検証テンプレート

```
Issue #XXX のフロントエンド実装をチームで検証して。
- コンポーネント担当: Container/Presentational 分離、Private Folder 構成の準拠
- データフェッチ担当: Server/Client 境界、キャッシュ戦略、ローディング/エラー状態
- UI/UX担当: レスポンシブ、アクセシビリティ、デザインシステム準拠
- 横断チェッカー: API契約との整合性、型の一貫性、状態管理の漏れ
```

### 禁止・非推奨パターン

| 場面 | 理由 | 代わりに |
|------|------|---------|
| 単一ファイルの修正 | 調整オーバーヘッドが効果を上回る | 単一セッション |
| 同一ファイルの編集 | 上書き競合が発生する | 単一セッション |
| 簡単な調査 | 結果を返すだけで議論不要 | サブエージェント |
| 単一ソースの調査 | 1つのドキュメントを読むだけ | サブエージェント or 単一セッション |

**注意事項:**
1. ファイル競合回避: 各メンバーが異なるファイルセットを所有
2. チームサイズ: 2-4人が適切
3. セッション制約: 1セッション1チーム
4. 十分なコンテキスト: メンバーに対象ファイルパス・既存パターン・制約を明示

### コンテキストフレッシュ戦略

#### 問題: 評価バイアスの蓄積

同一セッション内でレビュー・検証を繰り返すと、確認バイアス・アンカリング・疲労効果が発生する。

#### 解決: kill → spawn パターン

```
実装セッション → [kill] → 検証セッション（新規 spawn）→ [kill] → レビューセッション（新規 spawn）
```

#### 適用タイミングと強制度

| フェーズ | パターン | 強制度 |
|---------|---------|:------:|
| `/verify` Step 3-4 | サブエージェントを新規 spawn | **必須**（2レイヤー以上） |
| `/review` | 別セッションで実施 | **必須**（全 Issue） |
| `/verify` → `/review` 間 | セッション切替 | **必須**（全 Issue） |
| `/plan` Phase 3 リサーチ | サブエージェントに委譲 | 条件付き（2ソース以上） |

**ルール:**
1. 検証・レビューでは、前のフェーズのエージェントを再利用しない
2. サブエージェントには最小限の入力を渡す（Issue 本文 + `git diff` + テスト結果のみ）
3. 修正後の再検証でも新しいサブエージェントを spawn する

### Canonical 7 verb フェーズ別チーム活用ガイド

docdd-starters の canonical コマンド（`/issue` → `/plan` → `/worktree` → `/develop` → `/verify` → `/review` → `/pr` → `/merge`）に対応。

#### `/plan`: 計画立案フェーズ

| 条件 | モード |
|------|--------|
| 方針が明確（1ソース） | 単一セッション |
| 2ソース以上に分散するリサーチ | サブエージェント委譲 |
| 技術選定・設計トレードオフ | エージェントチーム |

#### `/develop`: 実装フェーズ

| 条件 | モード |
|------|--------|
| 単一レイヤーの変更 | 単一セッション |
| 2レイヤー以上にまたがる変更 | エージェントチーム |
| 重い調査で行き詰まった場合 | サブエージェント / Codex rescue |

#### `/verify`: 検証フェーズ

| 条件 | モード |
|------|--------|
| 単一レイヤーの変更 | 単一セッション |
| 2レイヤー以上にまたがる変更 | コンテキストフレッシュ spawn **必須** |
| DocDD 内容チェック | コンテキストフレッシュ spawn **必須** |

#### `/review`: 独立レビューフェーズ

| 条件 | モード |
|------|--------|
| 全 Issue | 別セッション **必須** |
| 大規模差分・複数レイヤー | 別セッション内でサブエージェント活用可 |
