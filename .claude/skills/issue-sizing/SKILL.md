# Issue サイジングスキル

## 概要

**1 Issue = 1 PR でレビュー可能なサイズに収める。**

Issue は「縦スライス」（1つの機能・概念が完結する単位）で切る。
「横スライス」（1レイヤーをまとめて対応）や「負債まとめて返済」は禁止。

**非ゴール**: Issue のフォーマット定義。それは `/issue` コマンドの責務。

## 使い方

以下のコマンドで参照される:
- `/plan` — Phase 1.6 のサイズチェックで参照
- `/issue` — Issue 作成時に影響範囲を概算
- `/brainstorm` — Issue 分割の判断時
- `/pr` — 1 PR = 1 Issue 原則の根拠として参照

## 詳細

### サイズ上限

| 指標 | 上限 | 超えたら分割 |
|------|:----:|:----------:|
| 変更対象ファイル | **20ファイル** | 必須 |
| 実装タスク数 | **8タスク** | 必須 |
| 起因 Issue / 負債 | **1つ** | 必須 |
| Phase 数 | **1** | 必須 |

> 上限はあくまで目安だが、**2つ以上超過したら分割を強く推奨**。

---

### 縦スライスの原則

#### 良い切り方（縦スライス）

1つの Issue で「1つのドメイン概念」または「1つの機能」が完結する。
**実装 + 関連 DocDD 更新を同じ Issue に含める**（サイズ上限内であれば）。

```
✅ 「ユーザーエンティティの追加」
   → Model + Service + API + Test + DM-User.md + ER図更新

✅ 「会員一覧API + 画面」
   → Model + Service + API + UI + Test + users.yaml 更新

✅ 「決済API追加」
   → Service + API + Test + DM-Payment.md + payments.yaml
```

> DocDD を別 Issue にするのは、サイズ上限（20ファイル）を超える場合のみ。

#### 悪い切り方（横スライス / まとめ返済）

```
❌ 「全テーブルのスキーマ定義」
   → レビュー不能、手戻り大

❌ 「未更新 Issue 3件分の DocDD 一括整備」
   → 18ファイル、20+タスク → レビュー困難

❌ 「API仕様書のカバー率向上」
   → 対象が広すぎてレビューが形骸化
```

---

### 分割の判断フロー

`/issue`（Issue作成）または `/plan`（計画立案）の時点で確認：

```
影響ファイル数を数える
  └→ 20ファイル以下 → そのまま進行
  └→ 20ファイル超  → 分割を検討
       └→ ドメイン概念ごとに縦に切れるか？
            └→ YES → 概念ごとに Issue を分割
            └→ NO  → Phase で分割（CRITICAL / HIGH / LOW）
```

---

### 負債返済の進め方

技術負債やドキュメント負債をまとめて返済したくなったら：

1. **棚卸し Issue** を1つ作る（調査・一覧化のみ）
2. 棚卸し結果から **概念ごとに個別 Issue** を作成
3. 個別 Issue を優先度順に1つずつ対応

```
✅ 正しい進め方
#100 棚卸し: DocDD 未更新の洗い出し（調査のみ）
#101 DM-User + Profile 更新
#102 DM-Payment + Invoice 更新
#103 API仕様書 カバー率向上（auth/users/payments）

❌ やりがちな間違い
#100 DocDD 一括整備（3 Issue 分の負債 + API全部）
```

---

### `/issue` `/plan` での適用

#### `/issue`（Issue 作成時）

Issue の概要を書いた時点で、影響範囲を概算する。
上限を超えそうなら、作成前に分割を提案する。

#### `/plan`（計画立案時）

影響範囲の特定後にサイズチェックを行う：

```markdown
## 📏 サイズチェック
| 指標 | 値 | 判定 |
|------|:--:|:----:|
| 変更対象ファイル | 6 | ✅ |
| 実装タスク数 | 5 | ✅ |
| 起因 Issue | 1 | ✅ |
| Phase 数 | 1 | ✅ |
```

超過した場合は分割案を提示してから計画を進める。

---

### 例外

以下のケースは上限を緩和してよい（ただし理由を明記）：

- **リネーム・一括置換**: 変更内容が機械的で、レビューが容易
- **テンプレート適用**: 同一パターンの繰り返しで、1ファイル確認すれば残りも同じ
- **マイグレーション**: スキーマ変更とモデル更新がセットで分割不可能

### Umbrella パターン

**Umbrella Issue** = 複数の関連 Issue（子 Issue）をまとめる親 Issue。
実装は子 Issue が担い、親は全体像・依存関係・共通設計の固定のみを担う。

#### いつ Umbrella 化するか

**分割先が 3 Issue 以上**、かつ以下のいずれかに該当する場合に提案する:

| 兆候 | Umbrella 化する理由 |
|------|-------------------|
| 基盤 + 複数適用の 1:N 構造 | 基盤を先行マージ必須にする依存順序を親で管理 |
| cross-cutting concern | 複数モジュール横断の共通設計を親で固定 |
| 同一テーマの段階実装 | 全子マージまで完了とみなさない進捗を親で追跡 |

#### Umbrella の構造

```
#親 [Umbrella] 機能名
  ├─ #子1 基盤（先行マージ必須）
  ├─ #子2 適用 1（#子1 後）
  ├─ #子3 適用 2（#子1 後、並列可）
  └─ ...
```

#### Umbrella 本体に書くこと（実装ではなく整合性管理）

- **子 Issue 一覧と依存関係**（どれが先行マージ必須か）
- **共有契約**（API 型・UI パターン・配置規約など、子で変更禁止の決定事項）
- **画面分類・スコープ切り分け**（子の担当範囲を重複なく覆う）
- **Umbrella レベルの検証定義**（全子マージ後に満たすべき状態、棚卸し表の有無）
- **完了条件**（子 Issue 全 CLOSE + Umbrella 固有 V の PASS）

#### Umbrella 本体に書かないこと

- **個別ファイル編集**（子 Issue の `/plan` で精密化する）
- **細かいタスク分解**（子 Issue の責務）

> **判定に迷ったら**: 分割先が 2 Issue 以下、または依存関係がない（並列完全独立）なら **Umbrella 不要**。単に関連 Issue 同士で Refs/Closes リンクを張れば十分。

---

### 観察集約パターン（Aggregate Observation）

複数の子 Issue で **同じ種類の問題が発生する可能性が高いが、現時点では断定できない** 場合に、共通化判断を遅延させるためのパターン。Umbrella 配下の「観察集約専用子 Issue」として起票する。

#### いつ使うか

以下を全て満たす場合:

- 親 Umbrella 配下の複数子 Issue（または独立した複数 Issue）が、**同種の cross-cutting concern** に触れる可能性がある
- ただし**現時点では発生有無 / 共通化パターン / 修正規模が確定できない**
- 共通化を**先回り**で実装するとミス判断のリスクが高い（実利用画面の API パターン差等）
- 各子 Issue 内で個別に直すと**共通化のチャンスを逃す**

#### 構造

```
#親 [Umbrella] 機能名
  ├─ #子1 適用 1 → 観察記録を #集約 にコメント
  ├─ #子2 適用 2 → 観察記録を #集約 にコメント
  ├─ #子3 適用 3 → 観察記録を #集約 にコメント
  └─ #集約 観察集約 + 一括修正（子1〜3 完了後着手）
       Status: Backlog（子完了まで待機）
```

#### 集約 Issue 本文に書くこと

- **観察対象画面 / 機能のリスト**（チェックリスト形式で進捗追跡）
- **観察記録テンプレート**（各子 Issue から本 Issue へコメント投稿する形式）
- **既知の観察記録**（起票時点で既にあれば 1 例として添付）
- **着手時のサイズチェック予告**（共通化規模次第で再分割判断する旨）

#### 各子 Issue への配線

各子 Issue にコメントで以下を投稿しておく:
- 集約 Issue 番号（#XXX）への参照
- 観察記録テンプレート
- 「対象画面を観察 → 集約 Issue へ記録コメント投稿」のチェックリスト

#### Umbrella パターンとの違い

| 観点 | Umbrella | 観察集約パターン |
|------|---------|-----------------|
| 親の責務 | 全体像 + 共有契約 + 依存関係 | 観察データの集約 + 共通化判断 |
| 親の実装 | しない（子が担う） | する（実装フェーズあり、ただし観察フェーズ後） |
| 着手タイミング | 子と並行 / 子完了後 | **必ず子完了後**（観察データが揃ってから） |
| サイズ判断 | 起票時点で固定 | **着手時に再判断**（観察規模次第で再分割可） |

> **注意**: 観察集約パターンは Umbrella の代替ではなく **補完**。Umbrella 配下の子の 1 つとして観察集約 Issue を置く。
