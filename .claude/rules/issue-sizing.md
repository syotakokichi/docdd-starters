# Issue サイジングルール

## 基本原則

**1 Issue = 1 PR でレビュー可能なサイズに収める**

Issue は「縦スライス」（1つの機能・概念が完結する単位）で切る。
「横スライス」（1レイヤーをまとめて対応）や「負債まとめて返済」は禁止。

---

## サイズ上限

| 指標 | 上限 | 超えたら分割 |
|------|:----:|:----------:|
| 変更対象ファイル | **20ファイル** | 必須 |
| 実装タスク数 | **8タスク** | 必須 |
| 起因 Issue / 負債 | **1つ** | 必須 |
| Phase 数 | **1** | 必須 |

> 上限はあくまで目安だが、**2つ以上超過したら分割を強く推奨**。

---

## 縦スライスの原則

### 良い切り方（縦スライス）

1つの Issue で「1つのドメイン概念」または「1つの機能」が完結する。
**実装 + 関連 DocDD 更新を同じ Issue に含める**（サイズ上限内であれば）。

```
✅ 「ユーザーエンティティの追加」
   → Model + Service + API + Test + DM-User.md + ER図更新

✅ 「会員一覧API + 画面」
   → Model + Service + API + UI + Test + members.yaml 更新

✅ 「決済API追加」
   → Service + API + Test + DM-Payment.md + payments.yaml
```

> DocDD を別 Issue にするのは、サイズ上限（20ファイル）を超える場合のみ。

### 悪い切り方（横スライス / まとめ返済）

```
❌ 「全テーブルのスキーマ定義」
   → レビュー不能、手戻り大

❌ 「未更新 Issue 3件分の DocDD 一括整備」
   → 18ファイル、20+タスク → レビュー困難

❌ 「API仕様書のカバー率向上」
   → 対象が広すぎてレビューが形骸化
```

---

## 分割の判断フロー

`/1`（Issue作成）または `/2`（計画立案）の時点で確認：

```
影響ファイル数を数える
  └→ 20ファイル以下 → そのまま進行
  └→ 20ファイル超  → 分割を検討
       └→ ドメイン概念ごとに縦に切れるか？
            └→ YES → 概念ごとに Issue を分割
            └→ NO  → Phase で分割（CRITICAL / HIGH / LOW）
```

---

## 負債返済の進め方

技術負債やドキュメント負債をまとめて返済したくなったら：

1. **棚卸し Issue** を1つ作る（調査・一覧化のみ）
2. 棚卸し結果から **概念ごとに個別 Issue** を作成
3. 個別 Issue を優先度順に1つずつ対応

```
✅ 正しい進め方
#100 棚卸し: DocDD 未更新の洗い出し（調査のみ）
#101 DM-User + Profile 更新
#102 DM-Payment + Invoice 更新
#103 API仕様書 カバー率向上（auth/users/payments）

❌ やりがちな間違い
#100 DocDD 一括整備（3 Issue 分の負債 + API全部）
```

---

## `/1` `/2` での適用

### `/1`（Issue 作成時）

Issue の概要を書いた時点で、影響範囲を概算する。
上限を超えそうなら、作成前に分割を提案する。

### `/2`（計画立案時）

影響範囲の特定後にサイズチェックを行う：

```markdown
## 📏 サイズチェック
| 指標 | 値 | 判定 |
|------|:--:|:----:|
| 変更対象ファイル | 6 | ✅ |
| 実装タスク数 | 5 | ✅ |
| 起因 Issue | 1 | ✅ |
| Phase 数 | 1 | ✅ |
```

超過した場合は分割案を提示してから計画を進める。

---

## 例外

以下のケースは上限を緩和してよい（ただし理由を明記）：

- **リネーム・一括置換**: 変更内容が機械的で、レビューが容易
- **テンプレート適用**: 同一パターンの繰り返しで、1ファイル確認すれば残りも同じ
- **マイグレーション**: スキーマ変更とモデル更新がセットで分割不可能
